# Trial run, 2026-10-20

A fresh agent was given the skills and `sp`, a small Node project (an in-memory notes store with two tests), and this request: add tags to notes, list notes by tag case-insensitively, and count notes per tag, with tags trimmed, lowercased, de-duplicated and empty tags rejected. There was no live user, so the agent wrote down each question and approval it would have asked for and assumed reasonable answers.

## What happened

- It sized the request as a feature and wrote a spec (requirements R1-R5 with acceptance checks) and a three-task plan. `sp spec check` and `sp plan check` passed.
- Every task went red then green through `sp test`. Two tasks were normal risk and one low risk.
- The self-review of Task 1 found a real bug: a sparse array of tags (`[, "A"]`) stored `undefined` as a tag. It was recorded as a `changes` round, fixed test-first, and approved in a second round.
- `sp done` refused once, correctly, while the latest review still asked for changes.
- `sp finish` ran the full suite: 15 tests, 15 passing.

## Friction it reported, and what changed

| Report | Change |
|---|---|
| The small and feature sizes overlapped | The sizing table now asks whether the user would want a say before you build. |
| "Public API" made every exported function high risk | Risk levels are defined with examples in the planning skill. |
| High risk needed a fresh reviewer, but there were no sub-agents | High-risk approval now needs `--by agent` or `--by user`. Without sub-agents, ask the user. |
| No per-task diff for uncommitted sequential tasks | The reviewing skill explains both the committed and uncommitted cases. |
| A red run could be any failure | `sp test --match "<test name>"` counts a run only if its output names the test. |
| Acceptance values were copied into the plan and the tests | Plans no longer copy them. `sp next` / `sp show` put them in each task's brief. |
| The report left out minor findings from approving reviews | The report lists every finding, ruling, run and plan change. |
| Long test output | `--tail <lines>` |

A later independent code review found further gaps in `sp` itself, such as rulings that could skip review, plan syncs that could weaken recorded work, and missing locking. They were fixed, and each one has a regression test in `test/hardening.test.cjs`.

# Second trial, same day, after the fixes

A fresh agent handled two requests on a clean copy of the same project:

1. **A small change.** `remove()` should throw on non-integer ids. It used the quick path: test-first by default, low risk.
2. **A high-risk feature.** JSON export and import of all notes, where import replaces the data and must reject malformed input. It went through shaping, planning and building.

There were no sub-agents and no live user. The agent played the independent reviewer itself in separate passes, labelled those reviews "SIMULATED" in their notes, and wrote down the user approvals it assumed.

## What happened

- The final suite ran 34 tests, all passing.
- The high-risk review found a real problem: a crafted backup could set note ids near the safe-integer limit and cause duplicate ids. The fix was test-first and is recorded in the report.
- `sp` refused to close tasks four times, each time correctly:
  - a high-risk task with no review;
  - a high-risk task with only a self-review;
  - a task whose latest review asked for changes;
  - work continuing after an unsynced plan edit.

## Friction it reported, and what changed

| Report | Change |
|---|---|
| A red run that failed for the wrong reason (a bug in the test itself) was counted | Still a known limit. The report now shows how each red run failed, so a reader can spot this. |
| Spec edits were not tracked | Spec changes now count as drift: tasks cannot close until `sp sync`, and the edit is recorded. |
| A `sync --reason` with no task changes was lost | The reason is now always recorded. |
| Refused closes were only in the log | The report has a "Refused closes" column. |
| New untracked files were missing from the suggested review diff | The reviewing skill now says to run `git add -N <new files>` first. |
| The reviewing and building skills disagreed on high-risk review without sub-agents | Both now say high-risk tasks go to the user. |
| `sp help review` printed the general help | `sp help <command>` now shows that command. |
| A broken `Verify:` command passed `sp plan check` | The planning skill now says to run each Verify command once before approval. |

Still not detected: code changed after an approving review. The report lists the runs and reviews in order, but `sp` does not diff the code.
